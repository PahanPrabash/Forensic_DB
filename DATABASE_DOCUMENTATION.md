# Forensic Medicine Database System — Database Documentation

This document contains the relational design documentation required by the **CO2050 Database Systems Mini Project Assignment**, including the **Data Dictionary**, **Normalization Steps**, and **Backup & Recovery Procedures**.

## 1. Relational Schema & Data Dictionary

The database consists of 25 normalized tables structured to support all clinical forensic examinations, autopsies, evidence custody tracking, and court reporting. Below is the data dictionary for the core entities of the system:

### Table: `Patient`
Stores personal and medical registration details of patients (living victims) and deceased individuals.

| Column Name | Data Type | Constraints | Description |
| :--- | :--- | :--- | :--- |
| `PatientID` | INT | PRIMARY KEY, AUTO_INCREMENT | Unique identifier for each patient. |
| `FirstName` | VARCHAR(100) | NOT NULL | First name of the patient. |
| `LastName` | VARCHAR(100) | NOT NULL | Last name of the patient. |
| `DateOfBirth`| DATE | Nullable | Date of birth. |
| `Age` | INT | Nullable | Calculated or reported age. |
| `Gender` | ENUM | NOT NULL ('Male', 'Female', 'Other') | Gender of the patient. |
| `NIC` | VARCHAR(20) | UNIQUE, Nullable | National Identity Card number. |
| `Address` | TEXT | Nullable | Residential address. |
| `Phone` | VARCHAR(15) | Nullable | Contact phone number. |

---

### Table: `Case`
Represents a medico-legal case registered by the JMO department.

| Column Name | Data Type | Constraints | Description |
| :--- | :--- | :--- | :--- |
| `CaseID` | INT | PRIMARY KEY, AUTO_INCREMENT | Unique identifier for each case. |
| `CaseNumber` | VARCHAR(50) | UNIQUE, NOT NULL | Format: `CW/YEAR/XXX` (auto-generated by trigger). |
| `CaseType` | ENUM | NOT NULL ('Clinical', 'Autopsy') | Vertical categorizing the case. |
| `SubCategory`| VARCHAR(100) | Nullable | e.g. Trauma, Domestic Abuse, Sexual Abuse, Homicide. |
| `IncidentDate`| DATE | NOT NULL | Date when the incident took place. |
| `Status` | ENUM | DEFAULT 'Open' | Status of the case ('Open', 'Closed', etc.). |
| `PatientID` | INT | FOREIGN KEY -> `Patient` | Reference to the patient. |
| `AssignedDoctorID` | INT | FOREIGN KEY -> `Doctor` | Reference to the assigned JMO/Doctor. |

---

### Table: `Postmortem` (Autopsy)
Stores details regarding postmortem autopsies and external/internal findings.

| Column Name | Data Type | Constraints | Description |
| :--- | :--- | :--- | :--- |
| `PostmortemID`| INT | PRIMARY KEY, AUTO_INCREMENT | Unique autopsy record ID. |
| `PMNumber` | VARCHAR(50) | UNIQUE, NOT NULL | Postmortem serial number. |
| `CaseID` | INT | UNIQUE, FOREIGN KEY -> `Case` | 1:1 relationship with Case (Autopsy). |
| `DeathType` | ENUM | Nullable | e.g. Natural, Homicidal, Suicidal, Accidental. |
| `AutopsyDate`| DATETIME | NOT NULL | Timestamp of the autopsy procedure. |
| `ExternalFindings` | TEXT | Nullable | Notes on external injuries and signs. |
| `InternalFindings` | TEXT | Nullable | Notes on internal organs examination. |

---

### Table: `Evidence`
Tracks physical and biological evidence collected during clinical or autopsy exams.

| Column Name | Data Type | Constraints | Description |
| :--- | :--- | :--- | :--- |
| `EvidenceID` | INT | PRIMARY KEY, AUTO_INCREMENT | Unique evidence ID. |
| `CaseID` | INT | FOREIGN KEY -> `Case` | Reference to the associated case. |
| `EvidenceType`| VARCHAR(100) | NOT NULL | e.g. DNA, clothing, blood, weapon. |
| `BarcodeQR` | VARCHAR(200) | UNIQUE, Nullable | Tracking barcode or QR code reference. |
| `ChainOfCustodyStatus` | ENUM | DEFAULT 'In Custody' | Status ('In Custody', 'Transferred', 'In Lab'). |

## 2. Normalization Steps

To eliminate data redundancy, prevent update/delete anomalies, and enforce data integrity, the schema has been normalized up to **Third Normal Form (3NF)**:

1. **First Normal Form (1NF):**
   * All tables have a defined primary key (`PatientID`, `CaseID`, etc.).
   * There are no repeating groups or multi-valued attributes. For instance, instead of storing multiple items of evidence as a comma-separated list inside `Case`, they are split into separate rows in the `Evidence` table.
   
2. **Second Normal Form (2NF):**
   * The schema is in 1NF.
   * All non-key attributes are fully functionally dependent on the entire primary key (no partial dependencies). For tables with composite keys (like `RolePermission` on `RoleID` and `Module`), permission flags (`CanCreate`, `CanRead`) depend on both the role and the module.

3. **Third Normal Form (3NF):**
   * The schema is in 2NF.
   * There are no transitive dependencies. For example, staff attributes (name, role, email) are kept in the `Staff` table, and only the `StaffID` is stored in the `Doctor` or `User` tables. A change in a doctor's designation does not affect the user authentication data.

## 3. Database Backup & Recovery Procedures

To satisfy the operational requirement of demonstrating database backup and recovery:

### How to Backup
Run `mysqldump` to export the database structure and data to an SQL dump file:
```bash
mysqldump -u root -p forensic_medicine_db > forensic_medicine_db_backup.sql
```

### How to Restore
Run `mysql` to import the SQL dump file and recreate the database:
```bash
mysql -u root -p forensic_medicine_db < forensic_medicine_db_backup.sql
```

A Windows utility script is provided at the root folder: [backup.bat](file:///c:/ACCADEMIC/PROJECT/git/my_first_git_Project/Forensic/Forensic_DB/backup.bat) to automate this.
